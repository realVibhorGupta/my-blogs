When people hear load balancing, they think about distributing traffic evenly across servers. That is true, but that is only one part of the story. A real load balancer does much more.

A load balancer:

* Manages traffic routing
    
* Detects unhealthy servers
    
* Prevents server overload
    
* Maintains session consistency when needed
    
* Helps with zero downtime deployments
    

If you have ever wondered what actually happens when a user opens your app, this post will walk through it step by step.

## **What Problem Does Load Balancing Solve**

Imagine you have one backend server.

```plaintext
User → Server
```

This works for small apps.  
When traffic increases, the CPU hits 90 percent, memory spikes, requests slow down, users complain.  
So you add more servers.

```plaintext
Users → Server A
       Server B
       Server C
```

Now you need someone to decide which server gets each request.

Enter the load balancer.

## **High-Level Architecture**

```plaintext
Client → Load Balancer → Multiple Backend Servers
```

But what determines which server receives the request?  
That is where **load balancing algorithms** come in.

## **Common Load Balancing Algorithms**

AlgorithmHow it WorksGood For

**Round Robin**Send requests to servers in rotation | Basic web servers

**Least Connections**Send to server with the fewest active connections | Long running connections or APIs

**IP Hash**Route based on user IP | Session stickiness

**Weighted Round Robin**Give stronger servers more traffic | Mixed server sizes or hardware

Example scenario:  
If Server A has twice the CPU of Server B, you give Server A twice the traffic → Weighted.

## **Health Checks**

A good load balancer never trusts servers blindly.  
It pings them to check if they are alive.

Example **health check endpoint**:

```plaintext
GET /health
Response: 200 OK
```

If a server fails the check:

* Load balancer **removes it** from routing
    
* No human intervention required
    

This prevents downtime.

## **Session Stickiness (Very Common Issue)**

If your app stores session in memory on a single server and the next request gets routed to a different server, the user appears logged out.

To avoid this, you can:

1. Use **IP Hash**
    
2. Use **Session Affinity ("Sticky Sessions")**
    
3. Store sessions in a **shared data store** like Redis
    

The third is the most scalable approach:

```plaintext
Backend Servers → Redis (Stores Sessions)
```

Now user sessions survive scaling.

## **Zero Downtime Deployment Using Load Balancer**

When deploying updates:

1. Mark one server as **out of service**
    
2. Wait for existing connections to finish
    
3. Deploy new code to that server
    
4. Bring it back into rotation
    
5. Move to the next server
    

No user sees downtime.

This is called **rolling deployment**.

## **Example: NGINX Load Balancer Config (Simple)**

```plaintext
http {
  upstream backend {
    server backend1.example.com;
    server backend2.example.com;
    server backend3.example.com;
  }

  server {
    listen 80;

    location / {
      proxy_pass http://backend;
    }
  }
}
```

You now have a basic Round Robin load balancer.

To use Least Connections:

```plaintext
upstream backend {
  least_conn;
  server backend1.example.com;
  server backend2.example.com;
  server backend3.example.com;
}
```

## **When to Add a Load Balancer**

Add one when:

* CPU usage varies across servers
    
* You need horizontal scaling
    
* Your app needs high availability
    
* You plan zero-downtime deployments
    

## **Takeaways**

* Load balancers do more than split traffic.
    
* They detect unhealthy servers, handle sessions, and help deployments.
    
* The best load balancing strategy depends on the workload pattern.
    
* Shared session storage like Redis avoids login issues.
