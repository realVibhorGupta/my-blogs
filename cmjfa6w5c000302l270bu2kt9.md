## 1️⃣ The Production Problem (Why This Exists)

Everything worked fine in staging.

Then one day, **a single API key started making 30,000 requests per minute**.

* CPU spiked
    
* Redis slowed down
    
* Legitimate users started getting **429s**
    

We *already* had rate limiting.

It just wasn’t designed for **real traffic**.

> Rate limiting is easy to add.  
> Designing one that survives production is hard.

---

## 2️⃣ Why Rate Limiting Really Matters

Rate limiting isn’t just about blocking attackers.

It protects your system from:

* Accidental client bugs
    
* Sudden traffic spikes
    
* DDoS-like behavior
    
* Cost explosions (cloud, AI APIs, third-party services)
    

A **bad** rate limiter:

* Blocks good users
    
* Breaks under load
    
* Becomes a bottleneck itself
    

A **good** rate limiter:

* Is fast
    
* Works across servers
    
* Is fair
    
* Is configurable (user, IP, API key)
    
* Fails safely
    

---

## 3️⃣ What Are We Actually Designing?

We want a system that:

* Works in a **distributed environment**
    
* Supports **per-user, per-IP, per-API key limits**
    
* Has **low latency**
    
* Doesn’t overload Redis
    
* Fails gracefully (never takes the system down)
    

---

## 4️⃣ Rate Limiting Algorithms (When to Use What)

### Fixed Window Counter (Simple, Risky)

```plaintext
12:00 – 12:01 → 100 requests allowed
```

❌ Problem  
Users can burst at window boundaries.

✅ Use only for:

* Internal tools
    
* Admin APIs
    

---

### Sliding Window Log (Accurate, Expensive)

Stores timestamp of **every request**.

✅ Very accurate  
❌ Memory-heavy and slow at scale

Use only for:

* Low-traffic systems
    
* Billing & auditing
    

---

### Sliding Window Counter (Best Tradeoff)

Combines:

* Current window
    
* Previous window (weighted)
    

✅ Accurate enough  
✅ Efficient  
❌ Slight approximation

> Most production systems land here.

---

### Token Bucket (Best for APIs)

* Tokens refill at a fixed rate
    
* Each request consumes a token
    
* Allows small bursts
    
* Smooths traffic naturally
    

✅ Best UX  
✅ Cloud-friendly  
✅ Highly scalable

Used by:  
**AWS · Stripe · GitHub**

## 5️⃣ High-Level Architecture (Distributed Setup)

```plaintext
Client
  ↓
API Gateway / Load Balancer
  ↓
Rate Limiter Middleware
  ↓
Redis (Shared Store)
  ↓
Backend Services
```

**Key idea**

> Rate limiting must happen **before** business logic.

A shared store guarantees consistent limits across servers.

---

## 6️⃣ Redis Data Model (Production-Ready)

**Key**

```plaintext
rate_limit:{userId}:{endpoint}
```

**Value**

```plaintext
{
  "tokens": 12,
  "last_refill_timestamp": 1690000000
}
```

**TTL**

* Automatic cleanup
    
* No manual resets
    
* Prevents unbounded growth
    

---

## 7️⃣ Handling Redis Bottlenecks (Critical)

### ❌ What Breaks at Scale

* Multiple Redis calls per request
    
* Locks
    
* Blocking logic
    
* Rate limiter becoming a SPOF
    

### ✅ What Actually Works

* Lua scripts (atomic logic)
    
* Single Redis call
    
* Local in-memory cache for hot keys
    
* Graceful fallback (fail open if Redis is down)
    

> Never let rate limiting take your system down.

---

## 8️⃣ Per-User vs Per-IP vs Per-API Key

| Type | Use Case |
| --- | --- |
| Per-IP | Public APIs |
| Per-User | Authenticated systems |
| Per-API Key | SaaS, partners |
| Combined | High-security systems |

Most real systems use **layered limits**.

---

## 9️⃣ When the Limit Is Exceeded

Always respond clearly.

**HTTP Response**

```plaintext
429 Too Many Requests
```

**Headers**

```plaintext
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
Retry-After: 30
```

Never:

* Return 500
    
* Silently drop requests
    

Good headers = better developer experience.

---

## 🔟 A Real Production Mistake

We originally rate-limited **per IP**.

One office NAT = **50 users blocked together**.

**Fix**

* Per-user limits for authenticated APIs
    
* Per-IP only for anonymous traffic
    

Result:

* Support tickets dropped instantly
    
* Fair limits restored
    

---

## 1️⃣1️⃣ Final Takeaways

* Rate limiting must be distributed
    
* Token Bucket works best for APIs
    
* Redis Lua scripts &gt; multiple Redis calls
    
* Always return meaningful headers
    
* Never let rate limiting break your system
