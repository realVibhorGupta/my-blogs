## 1\. Hook — The incident nobody expected

One evening, our API was healthy.

* CPU: normal
    
* Memory: stable
    
* Latency: acceptable
    

Then traffic spiked.

Nothing crashed immediately.  
But slowly:

* Queues started growing
    
* Response times increased
    
* Downstream services began timing out
    

Finally, everything collapsed.

**The root cause?**  
We were accepting more work than the system could handle.

No backpressure. 🚨

---

## 2\. Context — Why this matters

Most systems fail **not because they can’t process requests**,  
but because they **accept unlimited requests**.

Backpressure is the mechanism that says:

> “Slow down. I’m at capacity.”

Without it:

* Retries amplify load
    
* Queues grow unbounded
    
* Latency explodes
    
* Cascading failures begin
    

Backpressure doesn’t make your system faster.  
It makes your system **survivable**.

---

## 3\. Breakdown — What backpressure really is

### What backpressure is NOT

* ❌ Just rate limiting
    
* ❌ Random request drops
    
* ❌ Increasing queue size
    

### What backpressure IS

A **feedback signal** from downstream to upstream saying:

> “I cannot handle more work right now.”

---

### Common backpressure techniques

#### 1️⃣ Bounded queues

Instead of infinite queues:

* Set a max size
    
* Reject or delay requests when full
    

This prevents memory explosions.

```plaintext
Producer → [Queue (max 10k)] → Consumer
                 ↑
           Backpressure kicks in
```

---

#### 2️⃣ Load shedding

When overloaded, intentionally drop:

* Low-priority requests
    
* Non-critical features
    

Better to lose **some traffic** than **the entire system**.

---

#### 3️⃣ Rate limiting with feedback

Not static limits.

Dynamic limits based on:

* CPU usage
    
* Queue depth
    
* Error rate
    

---

#### 4️⃣ Pull-based consumption

Instead of pushing work blindly:

* Consumers pull when ready
    
* Producers wait
    

Used heavily in:

* Kafka
    
* Reactive streams
    
* gRPC flow control
    

---

## 4\. Real case — How backpressure saved our system

In one production system:

* API accepted requests freely
    
* Background workers processed jobs
    
* Queue had no limit
    

During peak traffic:

* Queue grew to millions
    
* Workers lagged hours behind
    
* Deployments became impossible
    

**Fix:**

* Added bounded queues
    
* Rejected excess jobs early
    
* Returned `429 Too Many Requests`
    

Result:

* No memory spikes
    
* Predictable latency
    
* Graceful degradation under load
    

The system didn’t crash anymore.  
It **pushed back**.

---

## 5\. Key takeaways (Quick wins)

* Backpressure protects systems under stress
    
* Unlimited queues are a hidden time bomb
    
* Rejecting requests early is a feature, not a bug
    
* Stable systems say **“no”** when needed
    
* Backpressure prevents cascading failures
