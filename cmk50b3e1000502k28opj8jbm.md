## **1️⃣ The Promise Everyone Wants**

Every distributed system claims this goal:

> **“Each event will be processed exactly once.”**

No duplicates.  
No missing data.  
No retries gone wrong.

Sounds perfect.

In reality?

👉 **Exactly-once processing does not exist.**

---

## **2️⃣ Why Exactly-Once Sounds Reasonable (But Isn’t)**

On paper, it feels simple:

```plaintext
Message arrives → Process → Done
```

But distributed systems are not single machines.

They involve:

* Networks
    
* Multiple services
    
* Crashes
    
* Retries
    
* Partial failures
    

Once failures exist, **certainty disappears**.

---

## **3️⃣ The Core Problem: You Can’t Know What Happened**

Imagine this flow:

```plaintext
Consumer processes message
↓
Updates database
↓
Sends ACK to broker
```

Now failure happens **between steps**.

Questions you can’t answer:

* Did the DB update succeed?
    
* Did the ACK reach the broker?
    
* Should the message be retried?
    

You **cannot know for sure**.

This uncertainty kills “exactly once.”

---

## **4️⃣ Delivery Guarantees (The Real Options)**

There are only **three real delivery models**:

### **1\. At-Most-Once**

* Message delivered **0 or 1 time**
    
* No retries
    
* Data loss possible
    

Fast, unsafe.

---

### **2\. At-Least-Once**

* Message delivered **1 or more times**
    
* Retries allowed
    
* Duplicates possible
    

Safe, but messy.

---

### **3\. Exactly-Once**

* Message delivered **exactly 1 time**
    

❌ **Impossible in general distributed systems**

---

## **5️⃣ Why “Exactly-Once” Breaks in Practice**

### Network failures

ACKs can be lost.

### Consumer crashes

Processing may finish, but state isn’t recorded.

### Broker retries

Message gets delivered again.

### Partial commits

One system commits, another doesn’t.

**Retries create duplicates.  
No retries cause data loss.**

You must choose.

---

## **6️⃣ “But Kafka Has Exactly-Once Semantics?”**

Yes — **but with big asterisk (\*)**.

Kafka provides:

* Exactly-once **within Kafka**
    
* Using transactions
    
* With strict producer + consumer configs
    

Limitations:

* Only works inside Kafka ecosystem
    
* External systems (DBs, APIs) break guarantees
    
* Still requires idempotent consumers
    

Kafka gives **effectively-once**, not true exactly-once.

---

## **7️⃣ The Truth: Exactly-Once Is an Illusion**

In real systems:

> **You can’t guarantee exactly once delivery.  
> You can only design for safe duplicates.**

This shifts the problem from:  
❌ “How do I avoid duplicates?”  
✅ “How do I handle duplicates safely?”

---

## **8️⃣ What Actually Works: Idempotent Processing**

**Idempotency** means:

* Same message processed multiple times
    
* End result is the same as once
    

Examples:

* Deduplication keys
    
* Upserts instead of inserts
    
* Versioned updates
    
* Transaction IDs
    

Idempotency turns **duplicates into non-events**.

---

## **9️⃣ Exactly-Once at the Business Level (The Only Place It Matters)**

You don’t need exactly-once **delivery**.

You need exactly-once **effects**.

Example:

* Charge customer only once
    
* Create order only once
    
* Send email only once
    

Achieved by:

* Idempotency keys
    
* Unique constraints
    
* Transactional writes
    

---

## **🔟 Real Production Story**

A payment system tried to:

* Avoid retries to prevent duplicates
    

Result:

* Lost payments during outages
    

Fix:

* Enabled retries
    
* Added idempotency keys
    
* Accepted duplicate delivery
    
* Ensured single charge
    

Reliability improved immediately.

---

## **1️⃣1️⃣ Common Mistakes**

❌ Trusting “exactly-once” marketing  
❌ Disabling retries  
❌ Ignoring idempotency  
❌ Assuming message brokers solve everything  
❌ Designing for happy paths

Exactly-once fails when reality hits.

---

## **1️⃣2️⃣ What You Should Design For Instead**

✅ At-least-once delivery  
✅ Idempotent consumers  
✅ Deduplication logic  
✅ Transactional writes  
✅ Clear retry strategies

This is how **real systems survive**.

---

## **1️⃣3️⃣ Key Takeaways**

* Exactly-once is a myth in distributed systems
    
* Failures create uncertainty
    
* Retries are unavoidable
    
* Idempotency is the real solution
    
* Design for duplicates, not perfection

* Where can idempotency be added?
