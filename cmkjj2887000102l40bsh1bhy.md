1️⃣ The Problem I Didn’t See Coming

We shipped a clean event-driven system.

Services emitted events

Kafka topics were flowing

Consumers were happy

Then one day:

A service crashed mid-deploy

Some events were never published

Downstream systems silently diverged

The database had the truth.

The event stream did not.

That’s when CDC entered the conversation.

2️⃣ The Core Question

Should systems publish events explicitly?

Or should we read changes directly from the database?

This is the real debate:

Event Publishing

Change Data Capture (CDC)

They look similar. They fail very differently.

3️⃣ Event Publishing (The Traditional Way)

How It Works

Copy code

Application Code

├── Write to Database

└── Publish Event to Broker

Events are part of business logic.

Examples:

OrderCreated

PaymentCompleted

UserUpgradedPlan

4️⃣ Why Event Publishing Feels Right

✅ Clear domain intent

✅ Business-level events

✅ Easy to reason about

✅ Consumers get clean signals

This is Domain-Driven Design friendly.

5️⃣ But Event Publishing Has a Dark Side

Dual Write Problem

DB write succeeds

Event publish fails

Or worse:

Event publishes

DB transaction rolls back

Now your system lies.

6️⃣ Common Fixes (And Why They Still Hurt)

Retries → duplicates

Transactions → not cross-system

Exactly-once → myth

Kafka transactions → limited scope

Event publishing requires discipline.

7️⃣ CDC (Change Data Capture) Explained

How CDC Works

Copy code

Database WAL / Binlog

↓

CDC Tool (Debezium)

↓

Message Broker

↓

Consumers

No application code publishes events.

The database is the single source of truth.

8️⃣ Why CDC Feels Magical

✅ No dual writes

✅ No missing events

✅ Crash-safe

✅ Replayable history

✅ Works even if app is down

CDC captures facts, not intentions.

9️⃣ What CDC Actually Emits

CDC events look like this:

Copy code

Row before

Row after

Operation type (INSERT / UPDATE / DELETE)

Transaction metadata

This is data-level, not domain-level.

🔟 CDC’s Hidden Cost

CDC does NOT know:

Business intent

Why something changed

Which fields matter

You get:

“User row updated” Not: “User upgraded to premium”

Meaning must be reconstructed.

1️⃣2️⃣ Who Owns the Contract?

Event Publishing:

The producer owns the contract.

CDC:

The database schema becomes the contract.

Schema changes now break consumers.

1️⃣3️⃣ When CDC Breaks

CDC breaks when:

Columns are renamed

Tables are split

Schema migrations are rushed

DB internals change

CDC shifts responsibility to data governance.

1️⃣4️⃣ Event Publishing Breaks When

Developers forget to emit events

Error handling is wrong

Partial failures happen

Retry logic misfires

It breaks at runtime.

1️⃣5️⃣ The Hybrid Model (What Works Best)

Most mature systems use both.

Pattern

Transactional Outbox for domain events

CDC to stream the outbox table

This gives:

Business intent

Database-level durability

No dual writes

1️⃣6️⃣ Real-World Usage

CDC-heavy: Data lakes, analytics, replication

Event-heavy: Workflows, sagas, business logic

Hybrid: Payments, orders, user state changes

Big companies rarely choose just one.

1️⃣7️⃣ Design Rule of Thumb

Use Event Publishing when:

Meaning matters

Business workflows depend on it

Use CDC when:

Data completeness matters

You can’t afford loss

You need replayability.

1️⃣9️⃣ The Big Takeaway

Event publishing explains why

CDC explains what

Reliability lives in the database

Meaning lives in application logic

The best systems respect both.
