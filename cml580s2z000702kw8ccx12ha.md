1️⃣ The Incident Everyone Hits Once

We had a simple flow:

Save order in DB

Publish OrderCreated event

Other services react

It worked… until one deploy.

Orders existed in the database.

But events never reached Kafka.

Inventory was never reserved.

Payments never started.

The system was “healthy”.

The business was broken.

2️⃣ The Core Problem

How do you atomically update your database AND publish an event?

You can’t.

Not safely. Not across systems. Not with retries alone.

3️⃣ The Naive Approach (And Why It Fails)

Copy code

BEGIN TRANSACTION

INSERT order

COMMIT

PUBLISH event

Failure window:

DB commit succeeds ✅

Event publish fails ❌

Result:

Data exists

Event never happened

This is silent data loss.

4️⃣ “Let’s Publish First” Is Worse

Copy code

PUBLISH event

BEGIN TRANSACTION

INSERT order

COMMIT

Failure:

Event published

DB write fails

Now consumers see an order that does not exist.

5️⃣ Why Distributed Transactions Don’t Save You

You might think:

“Let’s use 2PC”

But:

Kafka doesn’t participate

Message brokers don’t lock

External systems can’t rollback

Distributed transactions don’t scale.

6️⃣ The Transactional Outbox Pattern

The outbox pattern says:

Write business data and events in the same database transaction.

Nothing crosses the network inside the transaction.

7️⃣ How the Outbox Pattern Works

Copy code

BEGIN TRANSACTION

INSERT INTO orders

INSERT INTO outbox\_events

COMMIT

Later:

A background worker

Reads outbox table

Publishes events

Marks them as sent

8️⃣ Why This Works

Because:

DB commit is atomic

Either both writes happen

Or neither happens

No more split-brain state.

9️⃣ The Architecture

Copy code

\[ API \]

↓

\[ Database \]

├── orders

└── outbox\_events

↓

\[ Outbox Publisher \]

↓

\[ Kafka / RabbitMQ \]

The database becomes the source of truth.

🔟 Outbox Table Example

Copy code

outbox\_events

\--------------

id

aggregate\_id

event\_type

payload

status (PENDING / SENT)

created\_at

Never delete. Only mark as sent.

1️⃣1️⃣ Publishing Is Eventually Consistent

This is intentional.

You accept:

Slight delay

Eventual consistency

In exchange for:

Reliability

Recoverability

Zero data loss

1️⃣2️⃣ What Happens on Failure

Scenario: Publisher crashes

Outbox rows remain

Status still PENDING

Publisher restarts

Events resume publishing

Nothing is lost.

1️⃣3️⃣ Duplicate Events Will Happen

Important truth:

Outbox guarantees delivery, not uniqueness

If publish succeeds but ACK fails:

Event may be sent again

Consumers must be idempotent.

1️⃣4️⃣ Outbox + Idempotency = Correctness

Best practice:

Event ID as unique key

Consumers store processed IDs

Duplicate = no-op

This combo powers real systems.

1️⃣5️⃣ Polling vs CDC-Based Outbox

Polling

Simple

Portable

More DB load

CDC (Debezium)

High performance

Low latency

Infra complexity

Both are valid.

1️⃣6️⃣ CDC-Based Outbox Flow

Copy code

DB WAL

↓

CDC Tool

↓

Message Broker

No polling. Near real-time.

1️⃣7️⃣ Common Outbox Mistakes

❌ Deleting outbox rows

❌ Publishing inside request thread

❌ No retry logic

❌ No idempotency

❌ Treating broker as source of truth

1️⃣8️⃣ Where Outbox Shines

Microservices

Event-driven systems

Payments

Orders

Audit logs

Anywhere data loss is unacceptable.

1️⃣9️⃣ Where Outbox Is Overkill

Simple CRUD apps

Low business impact

Single service systems

Don’t cargo-cult it.

2️⃣1️⃣ The Rule I Use in Production

If losing an event breaks the business:

👉 Use Transactional Outbox

If duplicates break the business:

👉 You already lost

2️⃣2️⃣ Final Takeaway

Databases are good at transactions.

Brokers are good at delivery.

The outbox pattern lets each do what it does best.

Reliable systems don’t guess — they persist.
