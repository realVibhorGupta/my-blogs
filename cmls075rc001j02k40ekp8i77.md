When your system is overloaded, the real challenge is not scaling.  
The real challenge is **deciding who should still be served**.

Large-scale systems at companies like **Netflix** and **Google** do not try to save every request.  
They deliberately allow **partial failure**.

That is load shedding.

---

## The uncomfortable reality

When incoming load is higher than your capacity, you have only two choices:

* fail randomly
    
* fail deliberately
    

Random failure causes:

* thread pools to fill up
    
* queues to grow
    
* timeouts and retries
    
* cascading failures across services
    

Load shedding is about **controlled failure**.

---

## The goal

Not:

> serve everyone slowly

But:

> serve the right requests fast  
> and drop the rest early

---

## The real enemy: partial failures

The most dangerous state is:

```plaintext
service is alive, but extremely slow
```

Why?

```plaintext
slow responses
   ↓
timeouts
   ↓
client retries
   ↓
more traffic
   ↓
even slower responses
```

This feedback loop turns a small overload into a full outage.


If you wait until after expensive work, you are already too late.

## Where load shedding must happen

```plaintext
Client
  |
API Gateway / Edge  ← best place
  |
Service
  |
Downstream / DB
```

Load shedding is most effective at the **edge** or **service entry point**.

# Core strategies

---

## 1\. Hard capacity limits

The simplest form.

```plaintext
max_inflight_requests = N
```

When the number of active requests exceeds the limit:

```plaintext
→ reject immediately
```

This protects:

* thread pools
    
* memory
    
* connection pools
    

But it treats all traffic equally.

That is usually not what the business wants.

---

## 2\. Priority-based dropping

Not all requests have the same value.

Example classification:

```plaintext
P0 – payments, order placement
P1 – active sessions / streaming
P2 – browsing
P3 – recommendations, analytics
```

When the system is overloaded:

```plaintext
drop P3 first
then P2
protect P0 and P1
```

### Visual

```plaintext
Requests
    |
    v
 classify by priority
    |
+----------+----------+-----------+
|   P0     |    P1    |   P2/P3   |
| critical | important| optional  |
+----------+----------+-----------+
  almost       limited      aggressive
  never drop                dropping
```

This is business-aware shedding.

---

## 3\. Partial feature shedding

Instead of dropping users, you drop **features**.

Typical examples:

* disable recommendations
    
* skip personalization
    
* avoid fan-out calls
    
* return cached or precomputed results
    

```plaintext
full response  →  degraded response
```

Pattern:

```plaintext
Request
   |
Is system overloaded?
   |
   +-- no  → full pipeline
   |
   +-- yes → skip expensive steps
```

This is extremely effective for feed, streaming and content platforms.

---

## 4\. Fairness-based shedding

Fairness means:

> one client or user should not consume most of the capacity.

Common mechanisms:

```plaintext
per-user rate limits
per-client quotas
token buckets
```

When load rises, heavy users are throttled first.

This protects the rest of the population.

---

## 5\. Business-value shedding

### (fairness vs business value)

This is the real trade-off.

**Fair approach**

```plaintext
everyone degrades equally
```

**Business-driven approach**

```plaintext
paid users > free users
checkout > browsing
external customers > internal tools
```

In real systems, business value almost always matters.

---

## The unavoidable tension

```plaintext
fairness  <---------------->  business value
```

If you do not define this explicitly, the system will make the decision  
for you — randomly.

---

## The most practical policy in production

A hybrid strategy:

```plaintext
protect:
  - critical flows
  - high-value users

rate-limit:
  - heavy users
  - abusive clients

shed:
  - optional features
  - background traffic
```

---

# A concrete example

For an e-commerce platform:

```plaintext
checkout
product browsing
recommendations
order history
```

Under overload:

```plaintext
checkout         → always admitted
browsing         → limited
recommendations  → disabled
order history    → served from cache only
```

Revenue and user trust are protected first.

---

# Detecting overload correctly

Do not rely only on CPU.

Better signals:

* inflight request count
    
* request queue depth
    
* thread pool saturation
    
* downstream timeout rate
    
* tail latency (p99 / p999)
    

Simple admission rule:

```plaintext
if inflight_requests > limit
or p99_latency > threshold
→ start shedding
```

---

# The critical rule: shed early

Bad design:

```plaintext
authenticate
call multiple services
read database
then reject
```

Good design:

```plaintext
admission check
reject
do nothing else
```

Early rejection is what protects the system.

---

# Load shedding without retry control fails

If clients retry aggressively:

```plaintext
dropped requests
     ↓
retries
     ↓
more load
```

Load shedding must be combined with:

* client backoff
    
* retry budgets
    
* server-side rate limits
    

---

# The failure loop you must break

```plaintext
overload
   ↓
latency rises
   ↓
timeouts
   ↓
retries
   ↓
more load
```

Load shedding breaks this loop at the very top.

---

# Designing priority safely

Never trust priorities sent by clients.

Assign priority at the gateway using:

* endpoint
    
* authentication claims
    
* user tier
    
* request type
    

---

# Hidden risk: starvation

If low-priority traffic is always dropped:

* background jobs
    
* data pipelines
    
* maintenance tasks
    

may never run.

You need capacity guarantees:

```plaintext
Total capacity
+-----------------------------------+
|   P0   |   P1   |     P2 / P3     |
+-----------------------------------+
  40%       30%          30%
```

Each class gets a minimum share.

---

# Implementation checklist

* perform admission control before business logic
    
* classify requests into priority classes
    
* protect critical user journeys explicitly
    
* allocate per-class capacity budgets
    
* drop features before dropping users
    
* combine with retry and backoff policies
    
* monitor tail latency, not averages
    

---

# Learning focus recap

### Partial failures

* controlled failure is better than random failure
    
* shedding early prevents cascading outages
    

### Priority-based dropping

* classify traffic
    
* protect critical and high-value requests
    

### Fairness vs business value

* fairness protects the user population
    
* business value protects core revenue
    
* production systems usually use a hybrid model
    

---

## Key takeaway

Load shedding is not an optimization.

It is a **survival mechanism**.

When you cannot serve everyone:

**drop deliberately,  
drop early,  
and drop based on user impact and business value — not infrastructure metrics.**
